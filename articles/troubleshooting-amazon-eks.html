What I learned troubleshooting Amazon EKS

Three problems from my EKS project that forced me to look below the surface: worker-node bootstrap, VPC discovery and Kubernetes pod capacity.

Technical article8 min readAmazon EKS · Terraform · Kubernetes
On this pageProject context1. Worker nodes2. Load Balancer Controller3. Pod capacityWhat changed in my approach

Project context

The project was built around a containerised 2048 application running on Amazon EKS. Terraform provisioned the AWS infrastructure, ArgoCD managed Kubernetes deployments from Git, GitHub Actions handled validation and release workflows, and Prometheus/Grafana provided monitoring. The interesting part was not getting the happy path working; it was understanding why the platform failed when different parts of AWS and Kubernetes did not line up.

The main lesson: an EKS error often appears in one layer while the actual cause sits somewhere else: IAM, networking, add-on bootstrap, controller configuration or scheduler limits.

1. Worker nodes failed to join the cluster

The EKS control plane was available, but the managed node group was unhealthy and Kubernetes had no usable worker nodes. That meant the cluster existed in AWS, but there was nowhere for workloads to run.

How I investigated it

I checked the node-group state, private-subnet routing, IAM permissions and the kube-system components involved in worker bootstrap. The investigation showed that the networking add-ons were part of the dependency chain for healthy node registration.

$ aws eks describe-nodegroup --cluster-name nabil-eks-cluster --nodegroup-name ...
$ kubectl get pods -n kube-system
$ kubectl get nodes

What fixed it

I made the core EKS add-ons explicit in Terraform and configured the VPC CNI so it was available before compute was brought up. After the change, the aws-node pods became healthy and the worker nodes registered in Ready state.

2. The AWS Load Balancer Controller could not discover the VPC

The controller installed successfully but kept restarting. The important clue was in its logs: it was trying to discover AWS environment details automatically and could not determine the VPC it needed to work with. Until that was fixed, it could not create the Application Load Balancer for the Kubernetes Ingress.

$ kubectl get pods -n kube-system
$ kubectl logs -n kube-system deployment/aws-load-balancer-controller

What fixed it

Instead of relying on instance-metadata discovery, I set the AWS region and VPC ID explicitly in the Helm values managed through Git. ArgoCD then reconciled the controller with the corrected configuration. The pod stayed running and the ALB was provisioned for the application.

What this taught me: automation is useful only when I understand which values are being discovered implicitly. In managed platforms, making an important dependency explicit can be safer and easier to troubleshoot.

3. Monitoring pods were stuck Pending

The application was healthy before the monitoring stack was added. After deploying kube-prometheus-stack, several monitoring pods remained Pending. At first glance it looked like a generic resource problem, but the scheduler message was more specific: Too many pods.

$ kubectl get pods -A
$ kubectl describe pod <pending-pod>
# ... Too many pods

The existing t3.small workers had exhausted the number of pod slots available to them. CPU and memory were not the primary constraint. I increased the managed node group to three workers and aligned the desired size in Terraform. Once the additional node became Ready, the Pending monitoring workloads scheduled successfully.

What changed in my approach

These issues changed how I troubleshoot Kubernetes on AWS. I now start by identifying which layer is actually reporting the failure, then check the dependencies underneath it rather than changing several things at once. I also pay more attention to controller logs, scheduler events and capacity limits before assuming an issue is simply CPU, memory or IAM.

The project gave me a clearer view of EKS as a collection of connected systems rather than a single managed service. Kubernetes scheduling, AWS networking, IAM, add-ons, controllers and GitOps all affect whether the platform behaves as expected.
