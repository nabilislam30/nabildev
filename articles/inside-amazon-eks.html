Inside Amazon EKS: How the Cluster Actually Works

Amazon EKS removes the burden of operating the Kubernetes control plane, but the rest of the cluster still depends on networking, compute, identity, storage and several Kubernetes components working together. This article breaks those layers apart and follows what actually happens inside an EC2-backed EKS cluster.

Amazon Elastic Kubernetes Service, or Amazon EKS, is AWS's managed Kubernetes service. The word managed can sometimes make EKS sound more automated than it really is. AWS operates the Kubernetes control plane for you, keeps it highly available and exposes the Kubernetes API, but that is only one part of a working Kubernetes environment. Your workloads still need compute capacity, nodes need to communicate with the control plane, Pods need IP addresses, identities need permissions, and applications often depend on DNS, load balancing and persistent storage before they can serve any traffic.

That distinction matters because an EKS cluster can show as ACTIVE in the AWS console while still being unable to run an application. ACTIVE means the managed control plane has been created successfully. It does not tell you whether worker nodes have joined the cluster, whether CoreDNS is healthy, whether Pods can obtain IP addresses, whether storage can be attached or whether the identity running kubectl has permission to do anything useful.

This article looks at EKS as a collection of interacting systems rather than one large AWS service. The focus is a traditional EC2-backed EKS architecture using managed node groups, rather than EKS Auto Mode or Fargate. The aim is to understand where each component lives, what responsibility it has and where to look when something fails.

01 — CONTROL PLANE

Control Plane

A Kubernetes cluster is divided broadly into two areas: the control plane and the data plane. The control plane decides what should happen in the cluster, while the data plane is where application workloads actually run. In a self-managed Kubernetes environment you would operate both sides yourself, including the API servers, etcd database, schedulers and controller managers. In EKS, AWS operates the control plane on your behalf.

The EKS control plane runs in infrastructure owned and managed by AWS. You do not receive EC2 instances for it in your account, and you are not responsible for patching the control-plane operating systems, maintaining etcd or replacing failed control-plane hosts. AWS distributes the control plane across multiple Availability Zones and operates multiple instances of its critical components so that the failure of a single host or Availability Zone does not normally take the cluster API offline.

That managed control plane contains the same fundamental components found in other Kubernetes distributions.

The API server

The Kubernetes API server is the main interface into the cluster. Almost every operation eventually goes through it. When you run:

terminal
kubectl get pods

or:

terminal
kubectl apply -f deployment.yaml

kubectl is communicating with the Kubernetes API server.

The API server does far more than simply accept YAML. It authenticates the caller, checks whether that identity is authorised, validates the requested resource and processes admission controls before allowing the desired state into the cluster.

You can retrieve the API endpoint for an EKS cluster using the AWS CLI:

terminal
aws eks describe-cluster \
  --name my-cluster \
  --query 'cluster.endpoint' \
  --output text

The result resembles:

example
https://ABCD123456.gr7.eu-west-2.eks.amazonaws.com

This address is not your application endpoint. It is the management endpoint for Kubernetes itself.

etcd

Kubernetes stores its cluster state in etcd, a distributed key-value database. It contains information such as Deployments, Pods, Services, Secrets, ConfigMaps and node registrations.

Suppose you submit:

yaml
spec:
  replicas: 3

Kubernetes is not storing the instruction as "start three containers immediately." It stores the desired state: this workload should have three replicas. Other Kubernetes components continuously compare that desired state with reality and attempt to reconcile the difference.

That distinction is central to Kubernetes. Instead of issuing a sequence of imperative instructions, you normally declare what you want the final state to look like.

AWS operates and protects the etcd layer in EKS. You do not SSH into it, configure its disks or build its replication topology.

Scheduler

The scheduler decides which worker node should run each Pod. It considers factors including available CPU and memory, node selectors, affinity rules, anti-affinity, topology constraints, taints and tolerations.

A common misconception is that the scheduler starts containers. It does not. The scheduler's responsibility is placement.

Conceptually:

flow
Pod: web-7f6d9
        |
        v
Scheduler evaluates nodes
        |
        v
Node A: enough CPU, correct labels
Node B: insufficient memory
Node C: blocked by taint
        |
        v
Pod bound to Node A

After that decision is recorded, the kubelet running on Node A is responsible for making the Pod actually run.

Controller manager

Kubernetes also runs a collection of controllers. A controller continuously observes a resource and attempts to make reality match the desired state.

For example:

example
Desired replicas: 3
Running replicas: 2

The Deployment and ReplicaSet controllers detect the difference and create another Pod.

Eventually:

example
Desired replicas: 3
Running replicas: 3

This continuous process is called reconciliation.

It is why Kubernetes can recover from many failures automatically. If a Pod disappears, the system does not necessarily treat that Pod as something that must be repaired. Instead, a controller recognises that the desired replica count is no longer satisfied and creates a replacement.

The most important distinction at this stage is therefore:

example
Control plane
    Decides and records what should happen

Data plane
    Executes workloads

AWS manages the first. You remain responsible for designing and operating much of the second.

02 — NETWORKING

Networking

Networking is one of the areas where EKS becomes more complicated than it initially appears because the control plane and the worker nodes belong to the same Kubernetes cluster but do not live in exactly the same network environment.

Your EC2 worker nodes normally live inside your VPC, within subnets that you selected when building the platform. The EKS control plane itself is AWS-managed infrastructure. AWS therefore needs a secure way for the managed control plane to communicate with resources in your VPC.

When an EKS cluster is created, you provide subnet IDs. That does not mean the control-plane servers are launched inside those subnets. Instead, EKS creates Elastic Network Interfaces, commonly called ENIs, in selected subnets.

An ENI is effectively a virtual network card inside a VPC. It has private IP addressing and security-group associations and provides connectivity between AWS-managed EKS components and resources inside your network.

This is also one reason subnet sizing matters. Subnets are not simply containers for EC2 instances; they provide the finite pool of addresses used by nodes, Pods, load balancers and EKS networking components.

API endpoint access

The Kubernetes API endpoint can be configured for:

example
Public access
Private access
Public + private access

You can inspect the current configuration using:

terminal
aws eks describe-cluster \
  --name my-cluster \
  --query 'cluster.resourcesVpcConfig.{
    Public:endpointPublicAccess,
    Private:endpointPrivateAccess,
    PublicCIDRs:publicAccessCidrs
  }'

A typical development environment might enable both private and public access while restricting the public endpoint to known source addresses.

For example:

example
Public: true
Private: true
PublicCIDRs:
  - 81.100.20.30/32

The dangerous alternative would be:

example
0.0.0.0/0

That makes the API endpoint reachable from anywhere on the internet. Authentication is still required, so it does not make the cluster unauthenticated, but it unnecessarily increases the exposed attack surface.

Node-to-control-plane communication

Every worker node runs a kubelet. For the node to participate in Kubernetes, the kubelet must be able to communicate with the EKS API server over HTTPS.

Conceptually:

flow
Worker node
     |
     | HTTPS 443
     |
Kubernetes API endpoint
     |
     |
EKS control plane

During bootstrap, the node retrieves cluster information and authenticates to EKS. If that communication path fails, the EC2 instance may be perfectly healthy from an AWS perspective but never appear as a Kubernetes node.

That is why these two commands answer very different questions:

terminal
aws ec2 describe-instances

and:

terminal
kubectl get nodes

The first tells you whether EC2 exists and is running. The second tells you whether Kubernetes has successfully registered and accepted the node.

Control-plane-to-node communication

Traffic is not only node-to-control-plane. Some Kubernetes operations require the control plane to communicate back to services running on worker nodes.

For example:

terminal
kubectl exec -it my-pod -- /bin/sh

and:

terminal
kubectl logs my-pod

can involve the kubelet API, which commonly uses TCP port 10250.

This is why EKS security-group rules are important. A security group that appears restrictive from a normal web-application perspective may accidentally break required Kubernetes control-plane traffic.

Useful investigation commands include:

terminal
kubectl get nodes -o wide

and:

terminal
kubectl describe node <node-name>

For lower-level network inspection, you can also examine the cluster security groups:

terminal
aws eks describe-cluster \
  --name my-cluster \
  --query 'cluster.resourcesVpcConfig.clusterSecurityGroupId'

Networking problems in EKS often appear as Kubernetes problems because Kubernetes is the first layer that reports the symptom. The actual cause may be a route table, security group, subnet, DNS setting or endpoint configuration several layers below Kubernetes itself.

03 — WORKER NODES

Worker Nodes

The control plane cannot run your normal application workloads. Those workloads require compute capacity in the data plane.

In an EC2-backed EKS cluster, that compute comes from EC2 worker nodes. A worker node is an EC2 instance configured to join the Kubernetes cluster and run Pods.

A typical node contains several important components:

example
EC2 instance
│
├── Operating system
├── Container runtime
├── kubelet
├── Kubernetes networking components
└── Application Pods

The container runtime is the software responsible for actually running containers. Modern EKS-optimised images use containerd.

The kubelet is the Kubernetes agent running on each node. It registers the machine with the cluster, watches for Pods assigned to that node, communicates with the container runtime and reports Pod and node health back to the API server.

You can see registered nodes using:

terminal
kubectl get nodes

For example:

example
NAME                         STATUS   ROLES    AGE   VERSION
ip-10-0-11-25.eu-west-2     Ready    <none>   4h    v1.x
ip-10-0-31-48.eu-west-2     Ready    <none>   4h    v1.x

The important value here is:

example
STATUS: Ready

An EC2 instance being running and a Kubernetes node being Ready are not equivalent.

Running means the virtual machine exists.

Ready means Kubernetes can communicate with it and considers it capable of accepting workloads.

For more detail:

terminal
kubectl describe node ip-10-0-11-25.eu-west-2

This shows information such as:

example
Capacity
Allocatable resources
Node conditions
Taints
Pod CIDR/IP information
Running Pods
Allocated CPU/memory
Events

Managed node groups

EKS managed node groups provide an AWS-managed lifecycle around EC2 worker nodes. The instances still run in your AWS account and normally belong to an Auto Scaling Group, but EKS assists with operations such as provisioning, updates and draining nodes during replacement.

You can list node groups with:

terminal
aws eks list-nodegroups \
  --cluster-name my-cluster

Then inspect one:

terminal
aws eks describe-nodegroup \
  --cluster-name my-cluster \
  --nodegroup-name system-nodes

You may see scaling configuration such as:

example
minSize:     1
desiredSize: 2
maxSize:     3

These values describe EC2 capacity, but Kubernetes scheduling still happens independently. Increasing an Auto Scaling Group gives Kubernetes more machines; it does not decide which Pods go where.

Why bootstrap nodes matter

More advanced architectures commonly use Karpenter to provision nodes dynamically. Karpenter watches for unschedulable workloads and creates EC2 capacity that matches their requirements.

There is a bootstrap problem, however.

Karpenter itself runs as a Kubernetes Pod.

If the cluster has zero nodes:

flow
No nodes
   |
   v
Karpenter has nowhere to run
   |
   v
Karpenter cannot create nodes

The same issue affects other system workloads such as CoreDNS and storage controllers.

A common design is therefore:

flow
Small managed node group
        |
        v
Core cluster services start
        |
        v
Karpenter starts
        |
        v
Application workloads appear
        |
        v
Karpenter provisions additional capacity

The managed node group becomes the bootstrap layer rather than the main source of application capacity.

This is an important infrastructure-design lesson: even an autoscaling system may need some fixed capacity so that the autoscaling system itself can exist.

04 — IAM & RBAC

IAM & RBAC

Identity is one of the most confusing parts of EKS because two different security systems are involved:

example
AWS IAM
Kubernetes authorisation

They solve related but different problems.

AWS IAM establishes who or what is making an AWS-authenticated request.

Kubernetes RBAC, or Role-Based Access Control, determines what that identity can do inside Kubernetes.

A useful mental model is:

IAM establishes the AWS identity. EKS maps that identity into cluster access. Kubernetes authorisation determines what the identity can actually do.

Checking your AWS identity

Before troubleshooting Kubernetes access, check which AWS identity your terminal is actually using:

terminal
aws sts get-caller-identity

Example:

example
{
  "UserId": "AROAXXXXXXXXXXXXX",
  "Account": "123456789012",
  "Arn": "arn:aws:iam::123456789012:role/platform-engineer"
}

This becomes especially important when working with multiple AWS profiles.

For example:

terminal
AWS_PROFILE=nabil aws sts get-caller-identity

If the wrong AWS identity is being used, Kubernetes authentication will fail even if your kubeconfig looks correct.

kubeconfig

To configure kubectl for an EKS cluster:

terminal
aws eks update-kubeconfig \
  --region eu-west-2 \
  --name my-cluster

This adds cluster connection information to your kubeconfig, normally located at:

example
~/.kube/config

You can inspect the active context:

terminal
kubectl config current-context

and list available contexts:

terminal
kubectl config get-contexts

The kubeconfig contains information such as the API endpoint and certificate information. For EKS authentication, the AWS CLI is normally used to generate a short-lived token based on your current AWS credentials.

EKS access entries

Modern EKS clusters can use access entries to map IAM principals into cluster permissions.

List them with:

terminal
aws eks list-access-entries \
  --cluster-name my-cluster

You might see an identity such as:

example
arn:aws:iam::123456789012:role/platform-engineer

That access entry can be associated with EKS access policies or mapped to Kubernetes groups that are then controlled using normal Kubernetes RBAC.

This model is preferable to relying entirely on the older aws-auth ConfigMap for supported cluster configurations.

Kubernetes RBAC

Once an identity has entered the Kubernetes authentication system, Kubernetes still determines what it is allowed to do.

You can test permissions directly:

terminal
kubectl auth can-i get pods

Possible result:

example
yes

Then:

terminal
kubectl auth can-i delete deployments -n production

might return:

example
no

That distinction is important. A user could have significant AWS IAM permissions and still be denied access to Kubernetes resources.

Conversely, cluster administration privileges do not automatically mean that identity has broad AWS permissions outside the cluster.

Cluster role, node role and workload identity

Several IAM roles often exist around an EKS cluster, and they should not be confused.

The EKS cluster IAM role allows EKS to make required AWS API calls associated with the cluster.

The node IAM role is attached to EC2 worker nodes and allows node-level AWS operations such as accessing ECR for container images.

Application Pods should generally not inherit broad node-level AWS permissions. Workloads that need AWS services should instead use mechanisms such as EKS Pod Identity or IAM Roles for Service Accounts so that permissions are scoped to the workload.

Keeping these identities separate limits the impact of a compromised application.

05 — CLUSTER ADD-ONS

Cluster Add-ons

A healthy API server and several Ready worker nodes still do not guarantee that workloads are usable. Kubernetes depends on supporting components that provide Pod networking, DNS, Service routing and storage integration.

In EKS, several of these can be managed as EKS add-ons.

List installed add-ons with:

terminal
aws eks list-addons \
  --cluster-name my-cluster

You may see:

example
vpc-cni
coredns
kube-proxy
aws-ebs-csi-driver

You can also inspect the Kubernetes system namespace:

terminal
kubectl get pods -n kube-system

A healthy cluster might show resources such as:

example
aws-node-xxxxx
coredns-xxxxx
kube-proxy-xxxxx
ebs-csi-controller-xxxxx
ebs-csi-node-xxxxx

Each exists for a different reason.

Amazon VPC CNI

The Amazon VPC CNI integrates Kubernetes Pod networking with the AWS VPC.

CNI stands for Container Network Interface. It is the mechanism Kubernetes uses to configure networking for containers.

In standard EKS VPC CNI configurations, Pods receive addresses from your VPC networking environment rather than living behind a completely separate overlay network.

You can see Pod IP addresses using:

terminal
kubectl get pods -o wide

Example:

example
NAME           READY   STATUS    IP
web-abc123     1/1     Running   10.0.22.47
api-def456     1/1     Running   10.0.22.51

Those addresses consume real VPC IP capacity.

That introduces an EKS-specific scaling concern: subnet IP exhaustion.

You may have:

example
Plenty of CPU
Plenty of RAM
Healthy EC2 instances

while new Pods still fail because no addresses remain available.

Useful commands include:

terminal
kubectl get daemonset aws-node -n kube-system

and:

terminal
kubectl logs -n kube-system \
  -l k8s-app=aws-node \
  --tail=100

You should therefore design subnet CIDR ranges with Pod density in mind, not only the number of EC2 instances.

CoreDNS

Kubernetes applications rarely communicate using raw Pod IP addresses because Pods are ephemeral. A restarted Pod may receive a different address.

Kubernetes therefore provides Services, which expose stable names and virtual addresses.

For example:

example
postgres.default.svc.cluster.local

CoreDNS provides DNS resolution for those names.

Inside a Pod:

example
nslookup kubernetes.default.svc.cluster.local

can be used to verify cluster DNS.

If CoreDNS fails, applications may appear healthy but fail when trying to communicate with databases, APIs or other internal services by name.

You can inspect CoreDNS using:

terminal
kubectl get deployment coredns -n kube-system

and:

terminal
kubectl logs \
  -n kube-system \
  -l k8s-app=kube-dns

kube-proxy

kube-proxy helps implement Kubernetes Service networking on each node.

Suppose you have:

example
Service: api
ClusterIP: 172.x.x.x

and three backend Pods:

example
10.0.1.21
10.0.1.34
10.0.2.18

Clients talk to the stable Service abstraction rather than tracking each Pod individually. kube-proxy programs networking rules on the node so traffic can reach appropriate backends.

Inspect Services with:

terminal
kubectl get services

and their selected endpoints with:

terminal
kubectl get endpoints

or newer EndpointSlice resources:

terminal
kubectl get endpointslices

If a Service exists but has no healthy backend endpoints, requests have nowhere to go.

EBS CSI Driver

Stateful workloads often need storage that survives container recreation. On AWS, one common option is Amazon EBS.

CSI means Container Storage Interface. Kubernetes uses CSI drivers to communicate with storage systems.

A typical path looks like:

flow
PersistentVolumeClaim
        |
StorageClass
        |
EBS CSI Driver
        |
Amazon EBS volume
        |
Worker node
        |
Pod

Check storage resources using:

terminal
kubectl get pvc

and:

terminal
kubectl get pv

A PVC stuck in:

example
Pending

may indicate issues involving the StorageClass, CSI driver, IAM permissions, Availability Zone placement or available storage capacity.

You can inspect the claim:

terminal
kubectl describe pvc <pvc-name>

EBS also introduces an Availability Zone consideration because an EBS volume is associated with an AZ. Kubernetes therefore needs to schedule the consuming workload where that storage can be attached.

This is another example of AWS infrastructure influencing Kubernetes scheduling decisions.

06 — FROM KUBECTL TO POD

From kubectl to Pod

The easiest way to understand how all of these systems interact is to follow a deployment from the developer's terminal to a running application.

Consider this Deployment:

yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:latest
          ports:
            - containerPort: 80

You submit it using:

terminal
kubectl apply -f deployment.yaml

The important point is that kubectl does not SSH into a worker node and start an NGINX container.

Instead, several independent components participate.

Step 1: kubectl reads the cluster configuration

kubectl reads your kubeconfig and determines which Kubernetes API endpoint it should contact.

Check the active cluster using:

terminal
kubectl config current-context

For EKS, your AWS identity is then used to obtain authentication for the cluster.

Step 2: The API server receives the manifest

The request reaches the Kubernetes API server.

The API server performs authentication, authorisation and validation. Assuming the request is accepted, the Deployment becomes part of the cluster's stored desired state.

You can immediately inspect it:

terminal
kubectl get deployment web

At this point the application may still not be running.

Step 3: Controllers create lower-level resources

The Deployment controller recognises the new Deployment and creates a ReplicaSet.

Inspect it with:

terminal
kubectl get replicasets

The ReplicaSet then ensures the requested number of Pods exists.

The resource hierarchy is roughly:

flow
Deployment
    |
ReplicaSet
    |
Pods

This is why deleting an individual Pod from a Deployment does not normally remove the application permanently.

Try:

terminal
kubectl delete pod <pod-name>

Then:

terminal
kubectl get pods -w

The ReplicaSet creates a replacement because the desired replica count has not changed.

Step 4: The scheduler chooses nodes

New Pods initially have no node assignment.

The scheduler evaluates cluster capacity and scheduling constraints and selects an appropriate node.

Common reasons a Pod cannot be scheduled include:

example
Insufficient CPU
Insufficient memory
Node taints
Node affinity
Topology constraints
No suitable persistent-volume location

A Pod may remain:

example
Pending

Inspect it with:

terminal
kubectl describe pod <pod-name>

The events section often contains the most useful information.

You can also view recent events cluster-wide:

terminal
kubectl get events \
  --sort-by=.lastTimestamp

Step 5: kubelet receives the assignment

Once a Pod has been bound to a node, the kubelet on that node observes the change through the Kubernetes API.

The kubelet then asks the container runtime to create the containers described in the Pod specification.

If the image is stored in Amazon ECR, the node must be able to authenticate and pull it.

A problem here might produce:

example
ErrImagePull

followed by:

example
ImagePullBackOff

Inspect the Pod:

terminal
kubectl describe pod <pod-name>

Typical causes include:

example
Wrong image name
Wrong image tag
ECR permissions
Network connectivity
Registry authentication
Image does not exist

Step 6: Pod networking is configured

Before the Pod can communicate normally, the CNI plugin configures networking.

With the Amazon VPC CNI, the Pod is normally assigned an address associated with the VPC networking environment.

Watch this process using:

terminal
kubectl get pods -o wide -w

You may initially see:

example
NAME        READY   STATUS              IP
web-abc     0/1     ContainerCreating   <none>

and then:

example
NAME        READY   STATUS    IP
web-abc     1/1     Running   10.0.22.47

The appearance of a Pod IP is one indication that networking setup has progressed successfully.

Step 7: Storage is attached if required

If the Pod references a PersistentVolumeClaim backed by EBS, Kubernetes and the CSI driver must ensure the correct volume exists, attach it to the correct EC2 instance and mount it into the container.

A failure at this stage can leave the Pod stuck in:

example
ContainerCreating

even though the container image itself is perfectly valid.

Step 8: Health checks determine readiness

A running container is not automatically ready to receive traffic.

Kubernetes supports:

Liveness probes — determines whether a container should be restarted.

Readiness probes — determines whether the workload is ready to receive traffic.

Startup probes — useful for applications that take a long time to initialise.

Example:

yaml
readinessProbe:
  httpGet:
    path: /health
    port: 80
  initialDelaySeconds: 5
  periodSeconds: 10

If the readiness probe fails, the Pod may be:

example
Running

while still showing:

example
READY 0/1

That means the process exists but Kubernetes does not yet consider it a healthy backend.

Step 9: Services expose the workload

If you create a Service:

yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80

Kubernetes selects Pods matching:

example
app=web

You can inspect them:

terminal
kubectl get pods -l app=web

and the Service:

terminal
kubectl get service web

Application traffic can then move through a chain such as:

example
End user
Application Load Balancer
Kubernetes Service
Pod
Container

That complete path depends on AWS networking and Kubernetes networking cooperating correctly.

07 — PITFALLS

Pitfalls

A useful way to troubleshoot EKS is to stop treating every failure as an "EKS problem". EKS sits at the intersection of AWS infrastructure and Kubernetes, so symptoms can appear several layers away from the actual cause.

ACTIVE does not mean the cluster is ready

After cluster creation:

terminal
aws eks describe-cluster \
  --name my-cluster \
  --query 'cluster.status'

may return:

example
ACTIVE

That only confirms the control plane.

You should still check:

terminal
kubectl get nodes

and:

terminal
kubectl get pods -n kube-system

A useful readiness sequence is:

flow
Control plane ACTIVE
        |
Nodes Ready
        |
System add-ons healthy
        |
Workloads scheduled
        |
Application ready

EC2 running does not mean Kubernetes node ready

An EC2 instance can be:

example
running

while:

terminal
kubectl get nodes

shows nothing.

That immediately narrows the problem toward the bootstrap path between the node and the cluster.

Check:

terminal
aws sts get-caller-identity

then:

terminal
aws eks describe-nodegroup \
  --cluster-name my-cluster \
  --nodegroup-name <nodegroup-name>

and inspect node-group or Auto Scaling events.

Potential causes include:

example
Node IAM role
Security groups
Route tables
DNS
API endpoint access
Bootstrap configuration
Incorrect cluster name
Broken user data

IAM access does not equal Kubernetes access

An AWS administrator may still receive:

example
Error from server (Forbidden)

from Kubernetes.

Start with:

terminal
aws sts get-caller-identity

then:

terminal
aws eks list-access-entries \
  --cluster-name my-cluster

and finally:

terminal
kubectl auth can-i get pods

These commands test three different parts of the access path.

Subnet exhaustion can look like a scheduling problem

Because the VPC CNI uses VPC networking resources, IP addresses are part of cluster capacity.

A node can have spare compute while Kubernetes is still unable to create networking for additional Pods.

Check Pod events:

terminal
kubectl describe pod <pod-name>

and CNI health:

terminal
kubectl get pods \
  -n kube-system \
  -l k8s-app=aws-node

Subnet planning should therefore consider:

example
Nodes
Pods per node
Load balancers
EKS ENIs
Future scaling
Other resources using the subnet

not merely the current EC2 instance count.

Deployment order matters

Infrastructure dependencies are often invisible until Terraform attempts to create everything concurrently.

For example:

flow
EKS control plane
        |
Worker nodes
        |
CoreDNS / CNI
        |
Karpenter
        |
Application nodes
        |
Applications

Creating Karpenter before any compute capacity exists creates the bootstrap problem described earlier.

Terraform dependency relationships should reflect those architectural dependencies rather than assuming every resource can be provisioned independently.

Pending means something different from CrashLoopBackOff

Pod status can quickly narrow the investigation.

Pending commonly points toward:

example
Scheduling
Capacity
Volumes
Node selectors
Taints
Networking setup

ImagePullBackOff normally points toward:

example
Image name
Registry
ECR permissions
Network access

CrashLoopBackOff usually means the container starts and then repeatedly exits.

Check:

terminal
kubectl logs <pod-name>

For a repeatedly restarting container, inspect the previous instance:

terminal
kubectl logs <pod-name> --previous

ContainerCreating often means Kubernetes is still preparing:

example
Networking
Volumes
Container runtime
Secrets/configuration

Understanding those states prevents you from debugging an application crash when the real issue is storage, or debugging the VPC when the real issue is a broken container command.

A practical troubleshooting sequence

When something fails, it helps to investigate from the infrastructure layer upward rather than jumping randomly between AWS and Kubernetes.

Start with the control plane:

terminal
aws eks describe-cluster \
  --name my-cluster \
  --query 'cluster.status'

Then nodes:

terminal
kubectl get nodes

Then system components:

terminal
kubectl get pods -n kube-system

Then the workload:

terminal
kubectl get pods -o wide

Inspect the affected resource:

terminal
kubectl describe pod <pod-name>

Check recent events:

terminal
kubectl get events \
  --sort-by=.lastTimestamp

Then application output:

terminal
kubectl logs <pod-name>

If necessary, check permissions:

terminal
kubectl auth can-i get pods

and AWS identity:

terminal
aws sts get-caller-identity

This sequence works because each layer depends on the one beneath it.

A useful mental model is:

flow
Control plane
     |
Networking
     |
Worker nodes
     |
Identity
     |
Cluster add-ons
     |
Workload
     |
Application traffic

If a lower layer is broken, everything above it can produce misleading symptoms.

08 — CONCLUSION

Conclusion

Amazon EKS solves one of the most operationally difficult parts of Kubernetes by running the control plane for you. AWS provides the API-server infrastructure, control-plane availability and managed Kubernetes control components, but that does not remove the need to understand how the rest of the cluster works.

Worker nodes still need to start and register correctly. The Kubernetes API must be reachable. IAM identities need to become valid cluster identities. Pods need addresses from the VPC CNI, Services depend on Kubernetes networking, internal communication relies on CoreDNS and stateful workloads may depend on the EBS CSI driver before they can start successfully.

Once these responsibilities are separated, EKS becomes much less of a black box. A Pod that refuses to start is no longer simply an "EKS issue". It might be a scheduling constraint, a node that never joined the cluster, an IAM problem, an exhausted subnet, a failed image pull, a storage attachment issue, broken DNS or an application process that crashes immediately after launch.

The same understanding also changes how you design an EKS platform. Subnets become part of Pod capacity planning, IAM roles become separate trust boundaries, bootstrap nodes become infrastructure dependencies and cluster add-ons become essential platform services rather than optional Kubernetes extras.

That is ultimately the difference between being able to deploy an application onto EKS and understanding how the EKS platform is actually working underneath it.
