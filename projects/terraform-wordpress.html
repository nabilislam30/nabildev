WordPress infrastructure with Terraform

Provisioned a repeatable AWS environment with Terraform, including networking, routing, security and EC2 bootstrap for WordPress.

01 — Overview

What I built.

The goal was to replace a manual infrastructure setup with a repeatable Terraform configuration that creates the network and compute required to reach a WordPress installation. The project focused on understanding how the VPC, routing, security group and EC2 bootstrap fit together.

02 — Architecture

How the environment fits together.

  1. 01A VPC and public subnet provide the network boundary for the learning environment.
  2. 02An Internet Gateway and route table give the public subnet internet connectivity.
  3. 03A security group controls HTTP and administrative access.
  4. 04An Ubuntu EC2 instance runs the WordPress bootstrap process.
03 — Implementation

How it was implemented.

  1. 01Defined the VPC and public subnet in Terraform.
  2. 02Attached the Internet Gateway and configured the default route.
  3. 03Created security-group rules for the learning environment.
  4. 04Provisioned Ubuntu EC2 and used user data to install Apache, PHP and WordPress.
  5. 05Verified the build by reaching the WordPress setup page.

04 — Issues resolved

Problems I worked through.

  • Corrected VPC, Internet Gateway and route-table references while learning how the networking pieces depend on each other.
  • Fixed region-specific AMI and EC2-user assumptions that prevented successful instance access and bootstrap.
  • Worked through security-group and port-80 connectivity issues until the WordPress setup page was reachable.
  • Corrected user-data syntax and bootstrap errors so the instance could be configured repeatably.
05 — Outcome

Project outcome.

Terraform could reproduce the AWS environment and the EC2 bootstrap made the WordPress setup page reachable without manually configuring the instance after launch.

06 — Production considerations

What I would improve next.

  • Use remote Terraform state with locking.
  • Restrict administrative access and avoid broad SSH exposure.
  • Move application and data tiers into private networking where appropriate.
  • Use a managed database.
  • Add TLS, monitoring, backups and resilient load balancing.
