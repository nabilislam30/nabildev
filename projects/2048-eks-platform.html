2048 app on Amazon EKS

Built an Amazon EKS platform around a containerised 2048 application, with Terraform infrastructure, GitOps delivery, HTTPS, monitoring and security scanning.

01 — Overview

What I built.

The goal of the project was to deploy a containerised 2048 game application on Amazon EKS. The infrastructure was provisioned with Terraform and application deployments were managed through ArgoCD using a GitOps approach. CI/CD pipelines automated security scans, Docker image builds and release updates, while ArgoCD handled deployment to EKS. Dynamic DNS and SSL/TLS certificate management secured the application endpoint, and Prometheus/Grafana provided visibility into application and infrastructure health.

02 — Architecture

How the platform fits together.

  1. 01A custom VPC spans two Availability Zones with public and private subnets. Worker nodes run privately while the internet-facing ALB sits in the public networking layer.
  2. 02Amazon ECR stores immutable application images tagged with the Git commit SHA.
  3. 03Cloudflare manages the DNS zone, ExternalDNS manages the application record, and ACM provides TLS for 2048.nabilenv.com.
  4. 04ArgoCD manages the application, AWS Load Balancer Controller, ExternalDNS and monitoring stack from Git.
  5. 05Prometheus and Grafana provide cluster and workload visibility through the monitoring stack.
03 — Implementation

How it was implemented.

  1. 01Built reusable Terraform modules for the VPC, EKS cluster, ECR and IAM and composed them through a development environment in eu-west-2.
  2. 02Containerised the 2048 application and created Deployment, ClusterIP Service and Ingress manifests with CPU and memory requests and limits.
  3. 03Configured GitHub Actions to authenticate to AWS using OIDC. Pull requests run validation, Checkov and Terraform planning.
  4. 04Created an application release workflow that builds the image, scans it with Trivy, pushes to ECR and updates the image reference in Git.
  5. 05Enabled ArgoCD automated sync, pruning and self-healing.
  6. 06Deployed kube-prometheus-stack through ArgoCD and used Grafana dashboards to inspect cluster and workload metrics.

04 — Issues resolved

Problems I worked through.

01Node registration

Worker nodes failed to join the cluster

ProblemThe EKS control plane was running, but the managed node group kept failing and Kubernetes had no healthy workers.

FixI made the core EKS add-ons explicit in Terraform and configured vpc-cni with before_compute = true. The aws-node pods then came up and the workers reached Ready.

02VPC detection

Load Balancer Controller kept restarting

ProblemThe controller could not discover the AWS region and VPC through instance metadata, so it could not provision an ALB.

FixI set region: eu-west-2 and the VPC ID explicitly in the Helm values managed by ArgoCD. The controller stayed running and provisioned the ALB.

03Cluster capacity

Monitoring pods were stuck Pending

ProblemAfter adding kube-prometheus-stack, the scheduler reported Too many pods; the existing workers had exhausted available pod slots.

FixI scaled the managed node group to three workers and aligned Terraform to desired_size = 3. The Pending monitoring pods then scheduled successfully.

05 — Outcome

Project outcome.

The result was a production-grade Kubernetes platform on AWS capable of running, exposing, updating and monitoring a containerised application. The project gave me practical experience with deployment automation, platform reliability, security controls, observability, networking, IAM and cluster capacity.

06 — Production considerations

What I would improve next.

  • Add workload autoscaling and a clearer capacity strategy.
  • Strengthen environment separation and production approval controls.
  • Expand alerting and service-level monitoring beyond cluster dashboards.
  • Add stronger image promotion controls between build and deployment.
