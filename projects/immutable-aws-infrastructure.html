Immutable AWS infrastructure with Terraform

Built a production-inspired AWS platform around versioned Terraform modules, immutable compute, reviewed deployment workflows and automated drift detection.

01 — Overview

What I built.

The goal was to move beyond a single Terraform deployment and build a reusable infrastructure pattern with versioned modules, separate environments, controlled deployment identities, immutable compute and security guardrails. Infrastructure changes are reviewed and deployed through GitHub Actions rather than made manually in AWS.

Replaceable EC2 instances launch from a Golden AMI created by AWS Image Builder. The database tier stays private behind security-group controls.

02 — Architecture

How the platform fits together.

  1. 01Reusable modules are versioned independently from environment-specific live configuration and state.
  2. 02The VPC uses public, private application and database subnets with routing, NAT and VPC Flow Logs.
  3. 03AWS Image Builder produces the Golden AMI consumed by the launch template and Auto Scaling Group.
  4. 04An Application Load Balancer routes traffic to replaceable EC2 instances.
  5. 05Private PostgreSQL RDS uses KMS encryption, backups, Secrets Manager credentials and security-group-to-security-group access.
03 — Implementation

How it was implemented.

  1. 01Separated reusable modules from environment-specific live configuration and explicit Git module references.
  2. 02Built shared security, guardrail, IAM, monitoring and cost-control layers.
  3. 03Configured GitHub Actions to use OIDC, run Terraform validation and security checks, save reviewed plans and apply the approved plan artifact.
  4. 04Added scheduled Terraform drift detection across development, staging and production state targets using -detailed-exitcode.

04 — Issues resolved

Problems I worked through.

  • Least-privilege IAM: CI failures were traced to specific missing read or refresh permissions and expanded only where the evidence required it.
  • Security findings: scanner results led to changes around encryption, logging, state protection and permissions rather than being ignored as generic warnings.
  • Planning permissions: Terraform refresh exposed additional read access required by the pipeline, including load-balancer reads.
  • Image Builder drift: AWS normalisation produced Terraform differences that had to be understood before deciding whether the state or configuration should change.
05 — Outcome

Project outcome.

The completed platform demonstrates versioned Terraform modules, separated environment state, immutable AMI-based compute, ALB and Auto Scaling, private PostgreSQL RDS, OIDC-based deployment identities, security guardrails, reviewed-plan deployment and automated drift detection.

06 — Production considerations

What I would improve next.

  • Add compute and database workloads to staging and production.
  • Move environment access to SSM-only where appropriate.
  • Add Secrets Manager rotation where required.
  • Add formal database migrations for schema changes.
  • Introduce stronger independent production approval in a multi-user repository.
