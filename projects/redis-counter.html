Multi-container counter application

Built a Docker Compose stack with NGINX, multiple web containers and Redis-backed shared state.

01 — Overview

What I built.

The project demonstrates why shared state matters when an application is scaled horizontally. NGINX distributes requests across multiple interchangeable web containers, while Redis keeps the visitor count outside any one application instance.

02 — Architecture

How the application fits together.

  1. 01NGINX is the single entry point and reverse proxy.
  2. 02Three web containers can handle requests interchangeably.
  3. 03Redis stores the counter state so it is shared across all web instances.
  4. 04Docker Compose provides the private service network and container lifecycle.
03 — Implementation

How it was implemented.

  1. 01Containerised the Flask web application and Redis service.
  2. 02Added NGINX as the reverse proxy and entry point.
  3. 03Scaled the web service to three containers.
  4. 04Used Redis as shared state rather than storing the counter in one web container.
  5. 05Exposed the application through port 5050 and tested the counter endpoint.

04 — Issues resolved

Problems I worked through.

  • Port conflicts: local services were already using several ports, so the Compose configuration had to be aligned around a consistent external port.
  • Container/network conflicts: stale container names and networks caused startup failures and had to be cleaned up before recreating the stack.
  • Scaling: publishing the web container port directly conflicted with multiple replicas, so the web service used an internal exposed port and NGINX became the public entry point.
  • Shared state: the visitor counter had to live in Redis so requests handled by different web containers returned one consistent value.
05 — Outcome

Project outcome.

Requests are distributed through NGINX while all web containers use the same Redis-backed state, demonstrating reverse proxying, horizontal scaling and shared application state in a small containerised system.

06 — Production considerations

What I would improve next.

  • Add explicit health checks and restart policies.
  • Secure Redis and keep it private to the application network.
  • Add TLS at the edge.
  • Add metrics, logs and service dashboards.
  • Move to an orchestrator when availability and scaling requirements justify it.
