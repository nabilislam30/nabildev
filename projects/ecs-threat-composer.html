Threat Composer on AWS ECS Fargate

Built, containerised and deployed Threat Composer using Docker, Terraform and ECS Fargate, with ECR, HTTPS, a custom domain and GitHub Actions.

01 — Overview

What I built.

The project took a web application from local containerisation to a repeatable AWS deployment. Docker packaged the application, ECR stored the image, ECS Fargate ran the workload, and an Application Load Balancer exposed it over HTTPS through a custom domain. The infrastructure was then rebuilt in modular Terraform and connected to GitHub Actions.

The load balancer terminates HTTPS and forwards traffic to healthy Fargate tasks running the NGINX-served application image from ECR.

02 — Architecture

How the platform fits together.

  1. 01Route 53 resolves the custom domain to the Application Load Balancer.
  2. 02ACM provides the TLS certificate used by the HTTPS listener.
  3. 03ECR stores the application image consumed by the ECS task definition.
  4. 04ECS Fargate runs the workload without managing EC2 hosts.
  5. 05Security groups restrict inbound application traffic to the load-balancer path.
03 — Implementation

How it was implemented.

  1. 01Built a multi-stage Docker image and used NGINX as the runtime server with a /health endpoint.
  2. 02Validated the container locally before pushing the image to ECR.
  3. 03Built the networking, security, ACM, ALB and ECS resources in modular Terraform with remote state.
  4. 04Added GitHub Actions workflows using OIDC for infrastructure changes and application releases without long-lived AWS keys.
  5. 05Configured HTTP-to-HTTPS redirection and verified the live deployment through the health endpoint.

04 — Issues resolved

Problems I worked through.

  • NGINX permissions: running NGINX as a non-root user caused a PID-file permission error; moving the PID file to /tmp resolved it.
  • Certificate validation: ACM validation was delayed by hosted-zone/DNS issues, which required checking Route 53 records and the validation path.
  • ARM64 CI builds: emulated builds were slow, so the build process was adjusted to keep the build stage native while producing the required runtime image.
  • Yarn timeout: a CI network timeout was treated as a pipeline/network issue rather than an application defect and the timeout was increased.
05 — Outcome

Project outcome.

The final application runs on ECS Fargate behind an HTTPS Application Load Balancer and custom Route 53 domain. Images are stored in ECR, infrastructure is managed with Terraform, and GitHub Actions uses OIDC for infrastructure and application deployment workflows.

06 — Production considerations

What I would improve next.

  • Run tasks in private subnets and use private egress where appropriate.
  • Add ECS service autoscaling.
  • Add stronger image vulnerability scanning and promotion controls.
  • Add CloudWatch alarms and richer application observability.
  • Introduce staged environments and deployment approvals.
