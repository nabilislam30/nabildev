Hardening a Terraform delivery pipeline

A pipeline lab focused on safer Terraform validation, state handling, approvals and applying the exact reviewed plan.

Completed labTerraformAzure DevOpsS3DynamoDBYAML
Contact
01 — Challenge

The problem.

A pipeline could create infrastructure, but repeated execution and weak separation between plan and apply created risks around shared state and deploying changes that were not exactly the reviewed plan.

Architecture
Code pushValidateSaved planApprovalApply
02 — Implementation

How it was built.

  1. 01Added Terraform formatting and validation checks before planning.
  2. 02Moved Terraform state into S3 and added DynamoDB locking for a shared source of truth.
  3. 03Added guardrails to reduce the risk of deploying into the wrong AWS account.
  4. 04Generated a saved plan file and published it as a pipeline artifact.
  5. 05Added a manual approval point before applying the same reviewed plan artifact.
ci/cd · terraform
▋
03 — Troubleshooting

What required judgement.

  • Repeated runs exposed why local or unreliable shared state can cause duplicate infrastructure.
  • A fresh terraform apply after plan does not guarantee the exact reviewed plan is deployed.
  • Infrastructure changes benefit from an explicit control point before apply.
04 — Result

What worked.

The revised flow made validation, review and state handling more deliberate and reduced ambiguity between what was reviewed and what was deployed.

05 — Production considerations

What I would change next.

These are improvements I would make for a production-grade implementation; they are not presented as already completed.

  • Use workload identity or short-lived credentials instead of long-lived secrets.
  • Add policy-as-code and security scanning.
  • Add environment-specific approvals and protected branches.
  • Capture plan/apply logs centrally for auditability.
  • Introduce automated rollback or recovery procedures where the infrastructure design supports them.
